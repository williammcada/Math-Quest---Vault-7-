## 3. NF-ALARM-LIGHT-01 — visible red light on alarm cars

**Required outcome:** A player can recognize an alarm-equipped car by a visible red light on the vehicle, including when sound is muted. Ordinary cars must not receive the same alarm indicator.

Proposed state presentation:

| State | Presentation |
| --- | --- |
| Ready / unused alarm | A small, clearly visible red light slowly blinks on the car, allowing the player to identify it before touching or shooting it. |
| Alarm sounding | A stronger red light pulse/flash remains on the car for the entire active alarm interval, coordinated with the existing sound/effect state. |
| Spent / inactive after use | Stop the ready/active blink and leave the indicator off or visibly dim. Do not imply the alarm can be reactivated if the existing rules say it is spent. |

Place the light at an authored point on the vehicle, such as its dashboard/windshield or roof, aligned with the rotated sprite. It must not float beside the vehicle, be replaced by a debug outline, or disappear into the dark car artwork. Inspect the result at actual iPad/iPhone scale and through normal environmental lighting/occlusion.

The ready blink is a visual affordance, not an active distraction: it must not start audio, consume a charge, or attract enemies. Keep the existing touch/shot trigger, duration, AI diversion, garage-ingress exception, collision, and recovery behavior. This request does not authorize unlimited retriggering or another alarm balance change.

Use restrained local flashing, not a full-screen strobe. Preserve any supported reduced-motion behavior while retaining a readable alarm indicator. Exact placement, size, and cadence are visual tuning details to inspect before approval.

Acceptance: compare an ordinary car, an unused alarm car, an active alarm car, and a spent alarm car in live and DEV play; check pause, mute, recovery, and both mobile layouts. Confirm that the ready light is visible without causing a gameplay event.

## 4. MQ-BRAND-01 — separate platform identity from cartridge identity

### Naming hierarchy

Recommended stable conventions:

| Layer | Identity |
| --- | --- |
| Platform name | **MathQuest**; `MATHQUEST` is acceptable as the styled wordmark. |
| Platform mark | Neutral MathQuest wordmark or MQ emblem; no VII, vault door, or Nightfall symbol as the global default. |
| Product credit | **A WILLIAM MCADA PRODUCT**, preserved. |
| Cartridge titles | **Vault 7** and **Nightfall: Last Bus Out** in their own contexts. |
| Repository slug | Proposed `mathquest`, under the existing owner. Availability must be confirmed before execution. |
| Generic report/package prefix | `MathQuest`, with version or session identifier as appropriate. |

Do not solve the Vault 7 coupling by turning Nightfall into the new default platform identity.

### Interface changes

- The public landing page, teacher session builder, shared header/footer, generic join/loading/error/expired-session screens, diagnostics, and DEV hub use MathQuest identity.
- Replace the shared VII hero emblem with the neutral mark. Audit CSS backgrounds and pseudo-elements, not only visible text literals.
- Present each game within a clearly bounded cartridge card or selected-cartridge panel. Its title and artwork are legitimate there; they are not the platform banner.
- Prefer a neutral **Choose a cartridge** setup state for new sessions. Any retained selection must be explicit and correctly labeled, not a hidden fallback to Vault 7.
- Inside an identified session, show **MathQuest — [Cartridge title]** where both layers are helpful. Generic actions may use **Join session**, **Create session**, and **Return to MathQuest**; selected-cartridge actions may name that cartridge.
- Before session metadata resolves, show neutral MathQuest loading/join content. A Nightfall visitor must not briefly see Vault 7 branding during startup or reconnect.
- Page title, bookmark name, favicon, social preview metadata if present, accessible names, image alternative text, help headings, error messages, and export headings must match their context.
- Clear cartridge-specific title/theme when returning to the platform or switching cartridges.

### Data-driven presentation

Use the existing cartridge registry as the starting point. Have cartridge metadata supply title, artwork, emblem, theme, instructions, and relevant stage labels. Keep the global brand in one shared definition.

Avoid the present pattern of rendering Vault 7 first and patching the DOM for Nightfall. Unknown/missing cartridge metadata must produce a neutral loading/error state rather than silently rendering Vault 7. A third metadata entry should not require another brand-specific branch in generic UI code; this can be tested with a fixture, not a new playable cartridge.

### References that must remain

This is not a global search-and-replace of `vault`, `vault-7`, or `VII`.

Retain valid Vault 7 references in its own card, play/preview screens, story, help, assets, internal cartridge identifier, and reports of Vault 7 sessions. Keep `cartridgeId: "vault-7"`, related saved-state keys, and historical exports compatible unless a separately specified schema migration is necessary. Historical source URLs and migration records may name the old repository as provenance, not as a current recommended address.

A true report label such as **MathQuest session report — Vault 7** is permitted. A general site brand such as **Vault 7 mathematics platform** is not. Do not rename generic test evidence or mutate old JSON/CSV records to make the branding audit pass.

### Important migration facts

GitHub documents that repository links and Git operations follow repository renames, but **project-site URLs are excluded from automatic redirection**. Treat Pages bookmarks, old QR links, deep links, and the base path as a separate migration problem. Do not promise they will work merely because the GitHub repository link redirects. [G1]

Netlify documents that changing a project name changes its default hostname. Therefore the Netlify cleanup is an API-address dependency change, not just a dashboard-label edit. Do not assume the old hostname will remain usable. [N1–N2]

Browser local storage is partitioned by origin. A Pages path change under the same HTTPS hostname does not by itself change that origin, while changing a Netlify hostname does. Neither situation removes the need to test application keys, base paths, cache/service-worker scope where applicable, and recovery. Do not promise browser identity or teacher credentials automatically migrate across hostnames. [M1]
