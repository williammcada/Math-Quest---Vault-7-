# 1. Release purpose

MathQuest v0.9.1 is a stabilization, repair, clarity, reliability, and pilot-privacy release following hosted review of v0.9.

The release addresses problems that interfere with students:

* understanding Vault Seven objectives;
* understanding progression gates;
* interpreting equipment effects;
* navigating sensors safely;
* completing Nightfall interactions;
* understanding environmental hazards;
* using alternate escape routes;
* completing the cartridge without hidden collision or interaction failures.

It also adds the privacy controls required before the first classroom pilot.

v0.9.1 preserves:

* the mathematics engine;
* classroom session structure;
* MathQuest modular/cartridge architecture;
* academic/gameplay reporting separation;
* one live action run per student;
* existing teacher controls;
* reconnect behavior;
* existing GitHub Pages and service/relay architecture.

# 3. Vault Seven — verified baseline interpretation

The current Vault Seven implementation uses A, B, and C as checkpoint identifiers, but their player-facing meaning is too opaque.

### Checkpoint A

A is reached after the player completes the initial amber security-panel interaction.

It is both an objective and the first recovery checkpoint.

### Checkpoint B

B is an automatic mid-route recovery checkpoint.

It is **not** a terminal.

The player does not need to interact with an object to activate B.

### Checkpoint C

C is reached after completing the access-card objective.

It is the final recovery checkpoint before extraction.

### Elevator

The elevator is the final extraction endpoint.

The player interacts with it after securing the access card.

Checkpoint letters may remain in reports and compact HUD displays, but they must not be the sole explanation of the objective.

Each objective/checkpoint must provide:

* a recognizable visual object or location;
* readable prompt text;
* visible active/completed state;
* short completion confirmation.

# 5. Vault Seven — visual and progression redevelopment

The amber terminal, abstract door icon, drone, sensor bars, and checkpoint markers require clearer player-facing presentation.

## 5.1 Progression barriers

Replace opaque progression walls with visible story objects.

Every blocked route must correspond to something visible, such as:

* security door;
* shutter;
* physical barrier;
* containment gate.

Do not use an invisible collision wall as the primary representation of progression.

The collision footprint must match the visual object.

## 5.2 Door states

Doors or shutters must visibly communicate applicable states:

* LOCKED
* OPENING
* OPEN
* CLOSING
* JAMMED

When progression is blocked, show the missing requirement on or near the barrier.

## 5.3 Terminals

Interactive terminals require:

* recognizable console silhouette;
* screen/panel treatment;
* visible interaction area;
* obvious active state;
* readable Hold Interact prompt;
* progress feedback;
* completion feedback.

## 5.4 Drones

Patrol drones must read visually as patrol/security devices.

Provide:

* body;
* lens or sensor;
* search indication;
* readable patrol state;
* investigation/search animation or equivalent state feedback.

## 5.5 Sensors

Sensors should appear as physical security systems rather than arbitrary lines.

Acceptable presentation may include:

* emitters;
* scanning beams;
* floor grids;
* wall-mounted gates.

Active and inactive states must be understandable before collision/detection.

## 5.6 Text

Objective/state information should use crisp DOM or high-resolution overlay text where practical.

Do not rely on tiny low-resolution canvas text for important instructions.

# 6. Vault Seven — sensor timing and Maintenance Map

The previous Maintenance Map presentation is removed from the v0.9.1 gameplay target.

The former safe-zone presentation was not reliable enough because apparent safe geometry could conflict with actual sensor reach/timing.

## v0.9.1 decision

**Remove the Maintenance Map as a purchasable/action resource.**

Do not show unverified green safe rectangles.

Sensor information used by the game must reflect the actual emitter/timing model.

Where timing information is presented:

* use the actual sensor state;
* keep the information readable;
* avoid claiming a position is safe unless it actually is safe for the stated interval.

Accessible extraction choices must use the same underlying valid timing model.

---

# 7. Vault Seven — equipment

## 7.1 Silent Toolkit

Retain the Silent Toolkit.

The Toolkit remains the security-jam resource.

Requirements:

* make the effect visually obvious;
* show the affected device;
* show activation;
* show remaining state;
* preserve the intended one-use/checkpoint behavior already accepted by the current game design.

HUD states should clearly communicate:

* READY
* ACTIVE
* USED

## 7.2 Code Scanner

Retain the Code Scanner **only as cipher insurance**.

Its extraction beam forecast is removed because it is redundant when the beams are already visible.

Player-facing description should communicate:

**Cipher insurance active**

Do not imply that the Code Scanner is necessary for navigation or extraction.

## 7.3 Cloak

The final v0.9.1 decision replaces the earlier Ghost Beacon proposal with a **one-use Cloak**.

Requirements:

* one use per action run;
* five-second active duration;
* persistent consumed state so reconnect/recovery cannot restore the spent charge;
* clear READY state;
* clear ACTIVE state;
* clear USED state;
* visible activation feedback;
* visible end-of-effect feedback.

The Cloak is intended to create one temporary stealth opportunity.

Do not silently broaden the Cloak into a general security-system shutdown during recovery or later revisions.

Its recovered tested implementation should be preserved unless an explicit later specification changes it.

## 7.4 Persistent loadout HUD

The team loadout must remain visible during both Vault Seven and Nightfall.

Do not rely only on the pre-run briefing.

The HUD should show applicable resource state clearly enough that a student can tell:

* what the team purchased;
* whether an item remains available;
* whether an effect is currently active;
* whether the item has been consumed.

# 8. Vault Seven — audio

Vault Seven should include an actual music or ambient-score layer in addition to sound effects.

Requirements:

* bundled/local classroom-compatible audio;
* mute control;
* visible sound-status control;
* sound effects remain functional;
* optional audio failure must not block gameplay or academic submission.

# 9. Vault Seven — retained attempt policy

Unless superseded by a later release, preserve the existing base extraction attempt policy:

* three-minute active limit;
* three total detections;
* checkpoint recovery after the first two detections.

Failure behavior must remain understandable and must not alter academic mastery.

# 10. Nightfall — navigation and collision repair

Nightfall currently contains environmental collision that does not consistently match visible geometry.

This must be corrected.

## 10.1 Remove misleading billboard barriers

Remove the large purple billboard-style collision objects from the playable map.

Replace them with coherent world objects where solid geometry is needed.

Preferred replacement:

* burnt-out cars.

## 10.2 Collision rule

If the ground appears continuous and no solid physical obstacle is drawn, the player should normally be able to move through it.

Visible cars or other solid objects must have collision footprints consistent with their artwork.

Do not create invisible maze walls.

---

# 11. Nightfall — car alarms

Add at least three car-alarm objects.

Requirements:

* alarms are attached to identifiable cars;
* flashing red-light presentation;
* not represented as generic colored circles;
* only some cars contain alarms;
* alarms attract nearby enemies over a substantial area;
* sound attraction must respect walls/doors rather than passing unrealistically through solid geometry;
* use authored animation/sound/state feedback.

---

# 12. Nightfall — GAS barrels and fire

Add at least three generic flammable barrels labeled:

**GAS**

Requirements:

* recognizable barrel art;
* ignition state;
* warning state;
* explosion/fire animation;
* strong fire/smoke feedback;
* sound effect;
* clear damage cue.

## Damage decision

Fire/explosion is intentionally more dangerous to enemies than to the player.

### Player

A damaging fire/explosion contact removes approximately **50% of the player's maximum health**.

Use a brief damage cooldown/invulnerability window so one visual effect does not apply repeated frame-by-frame damage.

The player must receive:

* visible warning before/at ignition where appropriate;
* impact/damage feedback;
* understandable health loss.

### Enemies / mobs

Fire/explosion applies maximum or effectively lethal damage to ordinary mobs caught in the effect.

This makes environmental fire a meaningful tactical tool without making a single accidental player contact automatically equivalent to full-health death.

# 13. Nightfall — quest interaction repair

Broken or unreliable Search / Use interaction is release-blocking.

Audit the complete hosted interaction path for:

* fuse;
* power system;
* dispatch keys;
* battery;
* installation point;
* bus;
* survivor;
* any final required interaction.

Use one consistent interaction contract:

1. visible prompt;
2. valid proximity;
3. hold duration where required;
4. progress feedback;
5. completion confirmation;
6. server acknowledgement;
7. persistent completed state;
8. reconnect-safe result.

The survivor must be reachable and interactable without dependence on a narrow invisible collision region.

Add automated coverage where practical and perform a manual hosted end-to-end completion check.

---

# 14. Nightfall — breakable windows

Every enterable Nightfall room should contain one or two breakable windows where appropriate to the map.

A window can be broken by:

* shooting it; or
* holding Search / Use.

Both methods create noise equivalent to running.

Requirements:

* visible intact state;
* visible breaking animation/state change;
* visible broken state;
* actual passable opening after break;
* collision removed or changed to match the broken state;
* appropriate sound/noise behavior.

A visually broken window must not remain blocked by an invisible wall.

---

# 15. Nightfall — dispatch-key horde event

The final accepted trigger is:

**the player collecting the dispatch keys triggers the horde.**

Do not tie the trigger to the survivor collecting the keys.

When the player obtains the keys:

1. spawn a large horde at the dispatch door;
2. create immediate route pressure;
3. make the breakable-window escape mechanically relevant.

## Door behavior

If the dispatch door is open:

* the horde enters immediately.

If the dispatch door is closed:

* the horde is briefly delayed while breaking it down;
* show appropriate warning/animation;
* after the delay, the group breaches the room.

The horde should behave as a meaningful group/force multiplier rather than entering harmlessly in a slow single-file queue.

The room's window escape route must remain physically traversable.

# 16. Pilot privacy mode

Pilot privacy mode is required for the first classroom trials.

This is a MathQuest pilot configuration. It is not a claim that the application is anonymous by definition or that the hosting provider automatically provides the required privacy behavior.

The implementation must:

* minimize collection;
* avoid student real names;
* use generated aliases;
* limit retention;
* support teacher deletion;
* expire credentials;
* invalidate deleted/expired rooms.

---

# 17. Alias generation

Students must not be required to enter real names.

When a student device joins, the server assigns a non-identifying generated alias, for example:

`Nova-37`

Requirements:

* alias unique within the room;
* alias used in teacher dashboard;
* alias used in reports;
* no stored student-entered display-name/free-text field for the pilot.

Acceptance test:

Join using blank or arbitrary student-facing input where applicable and verify the stored roster contains generated aliases rather than real-name/free-text identity.

---

# 18. Opaque room identity

Use:

* random room code;
* separate random teacher credential.

Do not expose:

* student names;
* email addresses;
* class names;
* school directory identity;
* other identifying roster fields

inside:

* URLs;
* QR payloads;
* logs;
* reports.

Teacher and student access must remain room-scoped.

---

# 19. Data minimization

Pilot storage should contain only what is required for classroom operation and reporting.

Allowed categories include:

* device/session identifier;
* generated alias;
* team assignment;
* mathematics evidence;
* bounded gameplay evidence;
* necessary session/revision metadata.

Do not introduce:

* unrestricted student free text;
* advertising;
* analytics SDKs;
* third-party behavioral telemetry.

---

# 20. Retention

Default pilot retention:

**48 hours from room creation**

This falls within the approved short-retention window.

Requirements:

* store an explicit expiry timestamp;
* show the relevant expiry information to the teacher;
* polling does not extend expiry;
* ordinary room use does not extend expiry;
* expired room data is purged;
* expired room access is rejected.

A classroom should receive a fresh room rather than reusing an old room across classes.

---

# 21. Hosted-session deletion

The teacher must have a clearly labeled:

**Delete hosted session**

control.

Deletion requires confirmation.

After confirmed deletion, remove:

* session state;
* reports;
* roster/aliases;
* teacher credentials;
* gameplay evidence;
* other hosted room state.

Deletion is irreversible.

Test deletion against both:

* live room;
* ended room.

After deletion:

* state endpoint must fail;
* JSON report must fail;
* CSV report must fail;
* teacher credentials must fail;
* student room access must fail.

---

# 22. Credential expiration

Teacher credentials and room access become invalid:

* automatically at the retention deadline; or
* immediately after teacher deletion.

An expired or deleted credential must not:

* recreate the room;
* reveal old room state;
* issue commands;
* obtain reports;
* extend retention.

Test expired/deleted credentials against:

* state requests;
* teacher commands;
* report requests;
* deletion requests.

---

# 23. Post-expiry/deletion behavior

Old teacher and student tabs must receive a clear closure state.

Use a clear 410-style message such as:

> This pilot session has expired and was deleted.

Deleted sessions should display an equivalent deletion message.

Student tabs must stop indefinite polling after the server confirms that the room is closed/deleted/expired.

GradePal remains disconnected.

Do not introduce during v0.9.1:

* persistent learner identity;
* school-directory integration;
* educational-account login;
* GradePal writeback;
* unrelated external analytics.

# 25. Teacher privacy workflow

Recommended pilot classroom flow:

1. Teacher creates a fresh room.
2. System establishes room expiration.
3. Students join using the room/team flow.
4. Server assigns generated aliases.
5. Teacher conducts the session.
6. Teacher exports any required reports during the retention window.
7. Teacher chooses **Delete hosted session** after the pilot, or allows automatic expiry.
8. Next class receives a new room and new aliases.

Do not reuse a single pilot room across unrelated classes.

---

# 26. Reporting

Academic evidence and gameplay evidence remain separate.

Generated aliases may appear in both sections during the room lifetime so the teacher can connect results within that short-lived classroom session.

Reports must not contain:

* real names;
* email addresses;
* unrestricted free text;
* device hardware identifiers;
* IP-address reporting intended for teacher use;
* unrestricted raw event logs.

Bounded gameplay evidence may include:

* route;
* equipment;
* objectives;
* detections;
* action-game outcome;
* timing;
* accessibility mode;
* cartridge/revision data needed for supervision and balancing.

Reports should remain available during the retention window and disappear after deletion/expiry.

# 28. Verification status terminology

Use these statuses separately:

### Implemented

The required code/change exists in the candidate source.

### Automated tests passed

Applicable automated tests have passed against that exact candidate.

### Hosted tests passed

Teacher/student hosted flows and required deployment checks have passed.

### Classroom tested

The real school-device/network gate has actually been performed.

Do not collapse these into one generic claim that the version is "finished."

# 29. Release/checkpoint procedure

v0.9.1 should move through:

**IMPLEMENT → IMPLEMENTATION CHECKPOINT → VERIFY → VERIFIED CHECKPOINT → RELEASE → DEPLOY → CLASSROOM TEST**

Once the implementation has passed its required verification, preserve an identifiable source checkpoint before packaging.

Packaging or artifact-delivery failure must not require reconstruction of an already verified candidate.

Release packaging must use the verified candidate rather than a later untested source state.
